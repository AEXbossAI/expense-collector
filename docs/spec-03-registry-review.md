# Спек №3: Реестр, реконсилер и очередь разбора для фин директора

Источник: design doc `~/.gstack/projects/alex1/alex1-nogit-design-20260908-expense-collector.md`
Предшественники: `docs/spec-01-collectors.md`, `docs/spec-02-parser.md` — оба в проде
Спек 3 из 3, завершающий.

## Context

Система собирает документы и раскладывает их по папкам компаний. На 14.09.2026 из 21 расходного документа 15 разложились сами, 6 ждут человека. Но замкнуть цикл нечем:

- **Реестра нет.** В сентябрьской папке эстонской компании 17 файлов, и чтобы понять, что там лежит, надо открыть каждый. Дизайн называет реестр главным артефактом наравне с файлами.
- **Очередь некому разбирать.** Шесть документов ждут ответа на единственный вопрос «чья это компания», и спросить его пока негде.
- **Ответы никуда не копятся.** Каждый разбор спорного случая одноразовый: тот же вендор придёт в следующем месяце и спросит снова.
- **Ручные перемещения не видны.** Фин директор раскладывает документы руками — 8 из 17 файлов в сентябрьской папке положила она. Система об этом не знает.

Этот спек закрывает все четыре.

## Current State

Проверено на живой системе 14.09.2026.

| Что | Состояние |
|---|---|

| Реестр | Не существует |
| Очередь разбора | Не существует, документы просто лежат со статусом |
| Бот | `@orlanda_finance_bot`, в рабочем чате; личный чат с фин директором не заведён |

### Что показала разовая сверка

Скрипт `app/scripts/compare_inbox.py`, написанный для ответа на вопрос «чего нет в папках», обнаружил: **два документа Gamma уже лежали в папке компании, положенные фин директором руками**, а разборщик держал их в очереди, потому что в чеке Gamma покупатель не назван.

Отсюда два требования, которых не было в дизайне:
1. Реестр обязан включать документы, разложенные вручную, иначе он неполон и для закрытия месяца бесполезен.
2. Реконсилер обязан снимать с очереди то, что человек уже закрыл сам.

## Proposed Change

Три новые задачи в том же процессе плюс расширение телеграм-бота.

```
registry_loop     — раз в REGISTRY_DEBOUNCE_S, перегенерация затронутых реестров
reconciler_loop   — раз в 3 часа, сверка Dropbox с БД
digest_loop       — раз в сутки в DIGEST_HOUR, вопросы фин директору
```

### 1. Реестр

Файл `_реестр.csv` в каждой папке `<компания>/<год>/<Месяц_ГГГГ>/`.

**Формат: UTF-8 с BOM, разделитель `;`.** Без этого Excel в русской локали покажет всё одной колонкой. Проверяется открытием на машине фин директора, а не на сервере.

| Колонка | Содержимое |
|---|---|
| Файл | Имя файла в этой папке |
| Дата документа | `ДД.ММ.ГГГГ` |
| Вендор | Кто выставил |
| Назначение | Свободный текст, подсказка. **Не категория учёта** |
| Сумма | Число |
| Валюта | Код |
| Источник | Почта / Телеграм / **Вручную** |
| Примечания | «месяц по дате получения», «относится к закрытому ГГГГ-ММ», «вероятный дубль #N» |

**Перегенерация полная, из БД, идемпотентная.** Никаких инкрементальных дописываний: одна прерванная запись оставляет реестр битым навсегда.

**Дебаунс обязателен.** У фин директора стоит десктопный клиент Dropbox; перегенерация на каждый файл при открытом реестре плодит `conflicted copy`. Батч раз в N минут.

**При переклассификации перегенерируются реестры обеих затронутых пар (компания, месяц)**, иначе в старом остаётся строка-призрак.

### 2. Реконсилер

Раз в сутки, `files_list_folder` с сохранённым cursor по каждому корню компании (паттерн из `orlandabot/app/tasks/dropbox_sync.py`).

Обрабатывает четыре расхождения:

| Что нашлось | Что делаем |
|---|---|
| Файл есть в Dropbox, в БД нет | Заводим `Document` со `status=filed`, `source=manual`, вендора и сумму извлекаем разборщиком. **Реестр становится полным** |
| Файл в БД числится по одному пути, лежит по другому | Фин директор передвинула руками. Обновляем `dropbox_path` и `company`, перегенерируем оба реестра. **Человек прав, система подстраивается** |
| Файл в БД есть, в Dropbox нет | Удалён человеком. `status=ignored`, причина «удалён вручную». Не восстанавливаем |
| Документ в очереди, а его копия уже лежит в папке компании | Снимаем с очереди: `status=filed`, ответ известен. Сверка по `content_hash` |

Последняя строка — прямое следствие случая Gamma.

**Реконсилер ничего не удаляет и не перемещает.** Он приводит базу в соответствие с Dropbox, а не наоборот: источник правды по файлам — Dropbox, так записано в дизайне.

### 3. Очередь разбора в телеграме

**Адресат:** фин директор, личный чат с `@orlanda_finance_bot`. Ей нужно один раз нажать Start — без этого бот не может написать первым. Её `chat_id` попадает в конфиг (`FINANCE_CHAT_ID`).

**Дайджест раз в день** в заданный час. Одно сообщение, а не поток: при ста расходах в месяц уведомление на каждый чек читать перестанут через неделю.

**Вопросы сгруппированы по вендорам.** Три чека Bolt за неделю — один вопрос, ответ всё равно один:

```
Расходы, требующие решения — 4 позиции

1. Bolt (такси, Лимассол) — 3 документа, 71.00 EUR
   31.08 · 02.09 · 05.09
   [Эстонская]  [Израильская]  [Не распределять]

2. Wizz Air — авиабилет LCA-TLV, 40.00 EUR, 05.09
   [Эстонская]  [Израильская]  [Не распределять]
   ...
```

**Три кнопки, не две.** «Не распределять» закрывает случаи, когда расход реален, но компании не относится — личная покупка, чужой платёж, ошибочный документ. Решение владельца 14.09.2026 по лизингу Union Mobility: «вообще не берём расход». Без этой кнопки такой документ застревает навсегда и мозолит глаза в каждом дайджесте.

Документ уходит в `ignored` с причиной «не распределяем», файл откладывается в `_inbox/_ignored` (не удаляется), запись в базе остаётся журналом решения.

**Ответ применяется ко всей группе** и сразу запускает раскладку: файл уезжает в папку, реестр перегенерируется.

**Подтверждение дублей — тот же интерфейс.** Вопрос такой же бинарный: «Tonystam прислал счёт и подтверждение оплаты с одинаковым PDF — это один расход?» Кнопки `[Один расход]` `[Разные]`. Давать ей два разных инструмента незачем.

**Повторно один и тот же вопрос не задаётся.** Ответ по вендору запоминается на время, даже если правило ещё не создано.

### 3а. Компания по умолчанию

Решение владельца 14.09.2026: **чеки без указания покупателя относятся к эстонской компании**, «если прямо в чеке не написано обратного». Это такси, аренда авто, авиабилеты, подписки — всё, где документ выдан физлицу и юрлицо в нём не фигурирует.

Реализовано в разборщике как `DEFAULT_COMPANY`, применяется **только при полном отсутствии признаков**. Любое указание на израильскую компанию — идентификатор, название, иврит — отменяет умолчание.

Документ помечается `status_reason = "компания по умолчанию, в документе признаков нет"`, чтобы в реестре было видно: решение принято правилом, а не найдено в документе. Если фин директор с ним не согласна, она передвигает файл руками, и реконсилер подхватывает её решение.

**Эффект измерен:** очередь на разбор сократилась с 6 документов до нуля. Правило закрыло Bolt, Hertz Cyprus и Wizz Air, и закроет всех будущих вендоров того же типа, которых мы ещё не видели. Это сильнее, чем список правил по вендорам, который пришлось бы пополнять по одному.

**Остаточный риск:** израильский чек без единого идентификатора уедет в эстонскую папку молча. На корпусе из 14 израильских документов такой был один из четырнадцати. Ловится реестром и ручным перемещением, которое реконсилер увидит.

### 4. Накопление ответов и правила

Каждый ответ пишется в таблицу `routing_answers` **вместе с признаками**, а не только с идентификатором документа:

```python
class RoutingAnswer(Base):
    __tablename__ = "routing_answers"
    id, document_id, answered_at, answered_by
    company            # что выбрали
    vendor_normalized  # признак
    sender             # признак
    currency           # признак
    amount             # признак
    source             # признак
```

Запись «документ 5 → эстонская» через месяц бесполезна. Запись «вендор bolt, отправитель receipts-cyprus@bolt.eu, валюта EUR → эстонская» — материал, на котором видна закономерность.

Само правило — строка в таблице, которую проверяет код. Никакого влияния на промпт модели:

```python
class RoutingRule(Base):
    __tablename__ = "routing_rules"
    id, kind          # vendor | sender
    pattern, company
    created_from      # сколько ответов легло в основу
    confirmed_at, confirmed_by
    active
```

Закономерности **не предлагаются сами и никого не теребят**. Вместо этого — отчёт по требованию, командой боту или скриптом:

```
/закономерности

Bolt            → эстонская    3 ответа, разногласий нет
Gamma           → эстонская    2 ответа, разногласий нет
Union Mobility  → израильская  1 ответ
Wizz Air        → 2 эстонская, 1 израильская  ← правило не выводится
```

Противоречивые случаи показываются наравне с согласными. Отчёт, который прячет разногласия, подталкивает вывести правило там, где его нет.

**Создание правила — всегда явное действие человека.** Ни счётчик ответов, ни отсутствие разногласий сами по себе правило не включают.

**Промпт модели при этом не меняется никогда.** Правила — строки в таблице, которые проверяет код до обращения к модели. Промпт, переписывающий сам себя по накопленным данным, дрейфует незаметно: через месяц непонятно, почему документ раскладывается иначе, чем раньше.

**Правило применяется задним числом** к тем документам, что уже висят в очереди.

## Acceptance Criteria

1. В каждой папке `<компания>/<год>/<Месяц_ГГГГ>` с хотя бы одним документом лежит `_реестр.csv`.
2. Реестр открывается в Excel с русской локалью без искажений: колонки разделены, кириллица читается.
3. Реестр включает документы, разложенные фин директором вручную, с пометкой источника «Вручную».
4. Перемещение файла человеком между папками компаний обновляет `company` и `dropbox_path` в БД и перегенерирует оба реестра.
5. Удаление файла человеком переводит документ в `ignored`, файл не восстанавливается.
6. Документ из очереди, копия которого уже лежит в папке компании, снимается с очереди автоматически (случай Gamma).
7. Фин директор получает **одно** сообщение в день, если в очереди есть хоть что-то, и **ноль** сообщений, если очередь пуста.
8. Три чека одного вендора приходят одним вопросом, а не тремя.
9. Нажатие кнопки раскладывает все документы группы и перегенерирует реестр в пределах минуты.
10. Кнопка «Не распределять» переводит документы в `ignored` с причиной «не распределяем» и откладывает файлы в `_inbox/_ignored`; запись в базе сохраняется.
11. Подтверждение дубля оставляет один документ `filed`, второй `ignored` с ссылкой на основной; побеждает PDF, а не фотография.
12. Каждый ответ порождает строку в `routing_answers` со всеми признаками.
13. Отчёт `/закономерности` показывает и согласные ответы, и противоречивые. Правило не создаётся ни автоматически, ни по счётчику — только явным действием человека.
14. Включённое правило применяется к документам, уже висящим в очереди, и они уходят из неё без повторного вопроса.
15. Идентификатор компании в документе перекрывает правило.
16. Реестр не ломается при перегенерации во время открытого файла у фин директора (дебаунс).
17. Тесты написаны и проходят.

## Rollback Plan

- **Реестр:** файл `_реестр.csv` удаляется, ничего больше не затронуто. Полностью безопасно.
- **Реконсилер:** только читает Dropbox и пишет в БД. Файлы не трогает. Откат — `git revert` и сброс курсоров в `sync_cursors`.
- **Очередь:** нажатия кнопок приводят к перемещению файлов. Откат по журналу `MoveIntent`, как и в спеке №2.
- **Правила:** флаг `active=false` выключает правило, документы возвращаются в очередь.
- Деплой: `docker compose up -d --build --force-recreate` (**именно `--force-recreate`**).

## Открытые вопросы

1. **`chat_id` фин директора.** Нужен её Start боту. Без этого дайджест слать некуда.
2. **Час дайджеста.** Предлагаю утро по её часовому поясу (`TIMEZONE=Asia/Jerusalem`), уточнить у неё.
3. **Заводить ли в реестр 79 августовских файлов** эстонской компании или начать с сентября. Прогон реконсилера по августу даст полный реестр за месяц, но потратит около доллара на разбор и может вскрыть документы, которые фин директор считает закрытыми.
4. ~~Порог `RULE_MIN_ANSWERS`~~ — снят: правила не выводятся по счётчику, решение всегда за человеком.

## Правка 19.10.2026: файлы не удаляются никогда

Решение владельца после того, как разбор удалил из папок фин директора два файла
(документы 71 и 187), признав их «не расходом».

- В клиенте Dropbox нет операции удаления. Отброшенный файл, привезённый системой,
  откладывается в `_inbox/_ignored/<Месяц_Год>/<id>_<имя>` (`filer.set_aside`).
- Файл, положенный человеком (`source=manual`), система не перемещает, не
  переименовывает и не откладывает ни при каком решении.
- Ручной файл, который модель считает «не расходом», попадает в реестр с пометкой
  «ПРОВЕРИТЬ: модель считает, что это не документ расхода».
- Подтверждённый дубль: файл фин директора по умолчанию основной, экземпляр системы
  откладывается. Если оба экземпляра ручные, второй остаётся в папке, но в реестр не входит.
- Отброшенный моделью документ не закрывает файл навсегда: если тот же файл лежит в
  папке компании, сверка возвращает его в разбор. Решения человека остаются в силе.
- Месяц строки реестра — папка, где лежит файл; дата документа — только для записей
  без файла в папке компании. Реестр перезаписывается только при изменении содержимого.
- Ручной документ, разбор которого упал N раз, даёт алерт.
