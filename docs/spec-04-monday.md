## Context

Система собирает документы, раскладывает их по папкам компаний и держит реестр CSV в Dropbox. Реестр закрывает месяц, но не отвечает ни на один управленческий вопрос: сколько стоил проект, куда уходят деньги по категориям, что выросло по сравнению с прошлым месяцем. Всё это живёт в Monday, где уже есть проекты, клиенты, задачи и исходящие счета — а расходов нет вовсе.

Доска `🟣 5. Invoices` (`1550620081`) содержит группы `In` (исходящие счета, 368 items) и `Out` — **пустую**. Расходы едут в `Out`.

### Что показала разведка по боевым данным

Прогон по `db_expenses` 24.09.2026: 62 документа, 39 `filed`, 21 `ignored`, 2 `needs_review`. ## Решения владельца

| Вопрос | Решение |
|---|---|
| Что такое `Out` | Оплата. Расход фиксируем по чекам |
| Счёт без квитанции | **Едет всё равно, без всяких статусов** — квитанцию могли просто не положить |
| Валюта | Пересчитываем в EUR |
| Курс лари | По официальному курсу (для GEL официальный — Нацбанк Грузии) |

### Группы = месяцы

Айтемы плоские, «папки по месяцам» делаем штатным механизмом Monday — группами: `Расходы September_2026`, `Расходы October_2026`. Ключ группы совпадает с именем папки Dropbox (`naming.month_folder`), чтобы доска и папка сверялись глазами без пересчётов. Свёрнутая группа показывает сумму по колонке Amount сама.

Синк создаёт группу месяца, если её нет. Переключатель `MONDAY_GROUP_MODE=month|single` оставляет путь назад к единственной группе `Out` (`group_mm5x742`) одной правкой `.env` без релиза.

## Привязка к проекту

Каскад, сверху вниз. Каждый уровень слабее предыдущего, и слабый **не имеет права** переигрывать сильный.

### 1. Код задачи — детерминированно, без модели

```
TASK_CODE_RE = r"\b[A-Z]{2,4}-[A-Z]{2,4}-[A-Z]{2,4}-[A-Z]{2,4}-\d{4}-\d{2}-\d{1,6}\b"
```

Ищем во всех источниках: `original_name`, извлечённый текст документа, `raw_caption`, `raw_email_body`, тема письма. Дальше один запрос:

```graphql
items_page_by_column_values(
  board_id: 1542673123,
  columns: [{column_id: "text9__1", column_values: ["AMR-SAN-AQU-SC-2026-07-1677"]}]
)
```

Из задачи забираем `board_relation2__1` (проект) и `board_relation3__1` (вид услуги). `project_source = "task_code"`. Результат кэшируется в `monday_task_cache` навсегда: код неизменяем.

Два случая, которые надо обработать честно:

- **Несколько разных кодов в одном документе** (месячный счёт подрядчика на пять задач, сумма одна). **[решение D3]** В `board_relation_mm6chnqv` пишется проект задачи с наименьшим номером кода; все найденные задачи пишутся в `board_relation_mm6cqt3m` (у неё `allowMultipleItems: true`, проверено по `settings_str`); полный список проектов и кодов публикуется в Update айтема. Настройка колонки Projects не меняется — она общая с исходящими счетами, где связь 1:1 по смыслу. **Сумму не делим**: данных для сплита в документе нет. Разносить — только когда фин директор даст базу распределения.
- **Код найден, но в Monday не находится.** Проект не ставим, документ уходит в очередь человеку. Не гадаем: похожий код — это чужой проект, а не «примерно тот».

### 2. Название проекта в имени файла или тексте — нечётко

Справочник проектов подтягиваем с доски `1542627875` (группы `⚠️ Projects` и `✅ Completed Projects`), кэш `monday_projects_cache` на сутки. Нормализация: lower, подчёркивания и пунктуация в пробелы, схлопывание пробелов.

Три правила, в порядке убывания надёжности:

1. полное вхождение нормализованного имени проекта в нормализованный текст;
2. вхождение «ядра» — первых значимых слов имени длиной ≥ 5 символов, **при условии уникальности ядра среди всех 380 проектов**;
3. `difflib.SequenceMatcher` ≥ 0.85 по токенам — это опечатки: `orhot tota` ↔ `orhot tora` даёт 0.9.

**Правила 2 и 3 работают ТОЛЬКО по имени файла — исправлено 28.09.2026.**
Первая редакция применяла их и к тексту документа, и прогон на боевых данных
выдал чужой проект почти каждому накладному расходу: Anthropic ушёл на
«Port Market Tel Aviv», Tonystam на «m.a. green city Ltd», такси Bolt на
«Riding Tel-Aviv», конференция на «Matiani Tbilisi». Причина структурная:
в названиях проектов сидят обычные английские слова — `green`, `city`,
`market`, `begin`, `riding`, — и в многостраничном инвойсе такое слово
найдётся всегда. Имя файла человек пишет сам и коротко, поэтому совпадение
в нём означает намерение, а не совпадение.

По тексту ищется только полное название и только различимое, из двух
значимых слов: проекты называются «Island» и «Factory», искать такое слово
в тексте инвойса бессмысленно. Вхождение считается по границам слов —
подстрочный поиск давал «island» внутри «Highlands».

**Срабатывает только при единственном кандидате.** И вот честный пример, почему это важно: `orlanda_40375_static eilat.pdf` — слово «eilat» матчит и `Eilat project Plot 103-104-105-106`, и `Hotel Eilat`. Два кандидата → вопрос человеку, несмотря на то что код внутри документа даёт однозначный ответ. Здесь код сработает первым, но на документе без кода пришлось бы спрашивать, и это правильный исход.

Перед включением — офлайн-замер: `app/scripts/match_projects.py` прогоняет матчер по 380 именам проектов против имён всех уже собранных файлов и печатает попадания, промахи и неоднозначности. Порог 0.85 и правило уникальности ядра подтверждаются числами, а не на слово.

### 3. Правило по вендору

`RoutingRule` расширяется: `target` (`company` | `project`) и `project_monday_id`. Механика та же, что уже работает для компании: создаётся **только явным действием человека**, ни счётчик ответов, ни отсутствие разногласий правило не включают.

### 4. Вопрос в дайджест

Кнопки: пять проектов из последних ответов + `Общие расходы` + `Другой`. Ответ пишется в `RoutingAnswer(question="project")` вместе с признаками, как уже делается для компании, — `app/scripts/patterns.py` потом покажет закономерность или её отсутствие.

### 5. Пусто

`Привязка = Нет`. Для накладного расхода это норма, а не недоработка.

**Накладные расходы в очередь по проекту не идут вовсе.** Определяется по категории: `Подписки и ПО`, `Связь`, `Бухгалтерия`, `Юристы`, `Страхование` — общие по определению. Иначе фин директор получит тридцать бессмысленных вопросов в месяц и перестанет читать дайджест через неделю.

Общий принцип: **по умолчанию проект пустой, а не угаданный.** Одна ошибочная привязка в P&L проекта дороже ста пустых ячеек.

## Правки в существующем коде

Три места, без которых спек не работает. Все — корневые причины, не симптомы.

**`app/tasks/parser.py:99-101` — имя файла не доходит до разбора вообще.** Verbatim:

```python
    hint_text = doc.raw_caption or doc.raw_email_body or ""
    if hints:
        hint_text += "\n\nНайденные в тексте названия ..."
```

## Пересчёт в EUR

Оригинальные `amount` и `currency` не трогаем — они в реестре и в имени файла. Добавляем `amount_eur`, `fx_rate`, `fx_rate_date`, `fx_source`.

| Валюта | Источник | Формула |
|---|---|---|
| EUR | — | `amount_eur = amount`, запроса нет |
| Всё, что покрывает ECB (USD, ILS, …) | `api.frankfurter.dev/v1/{date}?base=EUR&symbols=X` | `amount_eur = amount / rate_X` |
| Всё остальное (GEL, AZN, …) | Нацбанк Грузии, кросс через лари | `amount_eur = amount * nbg(X) / nbg(EUR)` |

**НБГ — универсальный запасной источник, а не «источник для лари».** Он публикует
курсы в лари примерно для сорока валют, поэтому любая валюта вне набора ECB считается
кросс-курсом через GEL одной и той же формулой. Это важно практически: спек писался по
данным на 24.09, где валют было четыре, а на 28.09 в базе уже пять — приехали восемь
чеков Bolt из Баку в **AZN**, и AZN в наборе ECB тоже нет. Следующая командировка
добавит шестую; универсальное правило переживёт это без правки кода.

**Направление курса — самая дорогая ошибка в этом месте.** ECB отдаёт «единиц валюты за
1 EUR», НБГ отдаёт «лари за 1 единицу валюты». Перепутанное направление превращает
типографский счёт на 1720 GEL в 5147 EUR вместо 575 — тихо и правдоподобно. Тест на
каждую валюту обязателен, включая проверку, что GEL считается той же кросс-формулой,
что и AZN (`nbg(GEL)` тривиально равен 1).

Живые пробы 28.09.2026:
- `nbg.gov.ge/.../?currencies=EUR&date=2026-09-18` → `{"code":"EUR","quantity":1,"rate":2.9927}` — **лари за 1 EUR**;
- `nbg.gov.ge/.../?currencies=AZN&date=2026-09-27` → `{"code":"AZN","quantity":1,"rate":1.5343}` — **лари за 1 AZN**, отсюда 7.90 AZN ≈ 4.05 EUR;
- `api.frankfurter.dev/v1/2026-09-19?base=EUR&symbols=ILS,USD` → `{"date":"2026-09-18","rates":{"ILS":3.4812,"USD":1.146}}`;
- `api.frankfurter.dev/v1/currencies` — `GEL` и `AZN` отсутствуют оба.

Три детали, каждая из которых иначе уронит синк:

- **Откат на выходные делают сами провайдеры — своего цикла поиска не пишем.** Проверено: frankfurter на субботу 2026-09-19 вернул `"date":"2026-09-18"`; NBG на 20 и 21 сентября вернул курс от 19-го. Читаем поле `date` из ответа и пишем его в `fx_rate_date`. У NBG дата ответа лежит в верхнем `date`, а не в `validFromDate`.
- **Кэш обязателен.** Таблица `fx_rates` с уникальным ключом `(rate_date, currency)`: один запрос на валюту в день, а не на документ.
- **Курс не получен → item создаётся без суммы**, с Doc ID и пометкой, ретрай на следующем цикле. Сумма никогда не выдумывается и не берётся «примерно на сегодня».

## Один документ на расход

Сейчас на доску поедет всё `filed`, включая дубли. Нужен явный выбор представителя.

**Группа** — прямые соседи по любому из трёх признаков: `content_hash`, `business_key`, `doc_number` (новое поле, номер документа поставщика — надёжнее вендора с суммой). **Замыкание на один шаг, не транзитивное**: оба реальных случая — счёт и квитанция одним письмом, одно вложение двумя письмами — покрываются прямыми соседями, а полное замыкание на годовом объёме даёт N запросов на документ.

**Представитель** выбирается детерминированно, расширяем `dedupe.prefer`:

1. квитанция об оплате > счёт — потому что `Out` фиксирует оплату (требует нового поля `doc_kind`, его в модели нет);
2. PDF > фотография — текстовый слой, нет бликов и обрезанных краёв;
3. больший размер файла;
4. меньший `id`.

**[решение D5]** Порядок работ жёсткий, двумя коммитами. Сначала рефакторинг без
смены поведения: предикат кандидата в дубли выносится из SQL-запросов
`find_exact`/`find_business` в чистую `dedupe.is_dedupe_candidate(status, merged_into_id)`
и закрепляется тестом на текущее поведение (`filed`/`needs_review`/`probable_duplicate` —
кандидаты, `new`/`ignored`/`failed` — нет). Только потом добавляется условие
`merged_into_id is None` и новый ярус `prefer`. Причина: коммит
`665fe8a fix: пары документов помечали дублями друг друга и застревали` — этот баг
здесь уже был, и сейчас от него защищает только комментарий `dedupe.py:18-26`.

Не-представители получают `merged_into_id` = id представителя и на доску не едут вовсе. В Update айтема — строка «также получено: `<файл>` из `<источника>`», чтобы человек видел, что второй документ не потерян.

**Разовая чистка перед первым синком:** `app/scripts/merge_duplicates.py` печатает найденные группы и предлагает слить. Не автоматом — глазами, по образцу `patterns.py`. Ожидаемо: 39 `filed` схлопнутся примерно в 35.

## Обратная запись: правки человека не затираем

Фин директор поправит проект или категорию прямо на доске, и следующий синк это затрёт. Поэтому:

- храним `monday_last_written` (JSON) — что именно мы записали в прошлый раз;
- при обновлении пишем поле только если оно **пусто** на доске или **совпадает с тем, что мы писали** в прошлый раз;
- поле `Проект`, изменённое человеком, читаем обратно в `RoutingAnswer(question="project", answer=...)`;
- **правки `Amount`, `Vendor` и даты читаем обратно тоже.** Иначе фин директор исправит нашу сумму на доске, мы перестанем её перезаписывать — и в БД с `_реестр.csv` навсегда останется неверная. Расхождение доски и реестра даёт один алерт, как требует премиса 6 дизайн-дока: расхождения обнаруживаются, а не игнорируются.

Предпоследний пункт даёт обучение бесплатно: каждая ручная правка на доске становится материалом для правила, и `patterns.py` это увидит.

**`MONDAY_API_VERSION` пинуется обязательно.** Без заголовка Monday применяет версию
аккаунта по умолчанию и меняет её по своему расписанию, а формат ошибки лимита уже
менялся на версии 2025-07. В стеке это уже сделано дважды:

**Токен общий, и это осознанно.** Первая редакция спека требовала отдельный токен —
аргумент был неверный и снят. Замер на живом аккаунте 28.09.2026:

```graphql
query { complexity { before after query reset_in_x_seconds } }
# -> {"before":20000000,"after":19999969,"query":31,"reset_in_x_seconds":60}
```

**Бюджет сложности выделяется на аккаунт, а не на токен**, поэтому отдельный токен не
дал бы отдельного бюджета. Второй персональный токен Monday пользователю и не выдаёт:
перевыпуск заменяет старый и положил бы все шесть приложений, где он прописан. Настоящий
отдельный токен получается только вторым пользователем (платное место) или приватным
приложением с OAuth, а у app-токенов бакет 5M/мин против аккаунтских 20M — то есть хуже.

Что из этого следует для нас:

- Бэкфилл сентября (~120 вызовов) против 20M единиц в минуту — доли процента. Throttle
  `MONDAY_BATCH_SIZE` остаётся, потому что ничего не стоит, но защищает он от аккуратности,
  а не от реальной угрозы.
- **Ограничение, которое действительно общее, — суточный лимит вызовов** (1 000 / 10 000 /
  25 000 в зависимости от тарифа, тоже на аккаунт). Наш штатный расход ~105 вызовов в месяц,
  бэкфилл ~120 разово. На любом тарифе выше Free это незаметно.
- Остаются два честных следствия общего токена: правки на доске подписаны
  `alexeyb@orlanda.info`, а не сервисом; и ротация токена убивает expense-collector вместе
  с шестью остальными. Второе — строчка в `CLAUDE.md`, а не проект.

`MONDAY_SYNC_ENABLED=false` и `MONDAY_DRY_RUN=true` по умолчанию — ровно как `PARSER_DRY_RUN` в спеке №2. Сначала смотрим раскладку на боевых документах, потом она случается.

## Failure modes

| Сбой | Поведение |
|---|---|
| Monday 5xx, таймаут | ретрай с бэкоффом, строка живёт в `monday_pushes`; алерт при возрасте старейшей > 1 ч |
| Токен перевыпущен в другом проекте | синк встаёт с ошибкой авторизации и алертит; `MONDAY_API_TOKEN` общий с шестью приложениями, отдельный в Monday получить негде |
| Превышение бюджета сложности | **Monday отвечает 200 OK с массивом `errors`, а не 429.** `_gql` обязан бросать на непустом `errors[]`; `extensions.code == COMPLEXITY_BUDGET_EXHAUSTED` → спим `extensions.retry_in_seconds`, прочее → бэкофф и `last_error`. Отдельно обрабатываем HTTP 429 с `Retry-After`: обе формы встречаются в зависимости от версии API |
| Токен отозван | алерт, синк встаёт; разбор и раскладка не затронуты |
| Курс недоступен | item без суммы, ретрай; сумма не выдумывается |
| Код задачи не находится в Monday | проект не ставим, вопрос человеку |
| Нужного лейбла нет на доске | поле пустое, причина в `monday_error`, лейблы не создаём |
| Человек правит item руками | наши поля не перезаписываются, `Проект` читается обратно как ответ |
| Группа месяца не создалась | item не создаём, ретрай — item без группы потом не найти |
| Падение между `create_item` и записью `monday_item_id` | намерение пишется ДО вызова, как `MoveIntent`; подвисшие подбирает `sweeper`, проба восстановления — точечный `items_page_by_column_values` по Doc ID |
| Опечатка в `MONDAY_COLUMNS` | на старте синка один `get_board_info`: каждый id обязан существовать на доске **и быть нужного типа** (`EXPECTED_TYPES`), иначе алерт и синк не стартует. Тип важнее существования: значение дропдауна, записанное в status-колонку, Monday либо отвергнет, либо запишет мусором |

Предпоследняя строка — та же болезнь, что `MoveIntent` в спеке №2: транзакции между
Monday и Postgres нет. Лечится тем же приёмом, что уже работает в `filer.file_document`,
а не полным сканом доски: намерение до операции, `sweeper` после. Doc ID остаётся
обязательным как проба восстановления.

**Тихая потеря строки — главный риск этой интеграции.** Клиент, который смотрит только
на `resp.status_code`, при исчерпанном бюджете увидит 200 и пометит push успешным.
Расход не появится на доске **никогда**, и алерт по возрасту очереди этого не увидит,
потому что очередь пуста. Verbatim из `/opt/html-to-mailing/app/services/monday.py:199-206`:
«Monday answers 200 OK with an errors array for rate limits ("Complexity budget exhausted")
and bad queries alike».

**Параллельные полосы:**
`Lane A: S1 → S4 → S7` (общий `app/db/`, `app/services/`)
`Lane B: S2` (независим полностью)

**Порядок запуска:** запускаем A, B, C одновременно. Сливаем B и C. Затем S6 (нужны
все три). Затем S8. S7 может идти параллельно S6, если A уже слит.

`app/services/llm.py` (только S4) и `app/services/review.py` (только S7). Общий файл
`app/core/config.py` трогают S2, S3, S6 — сливать последовательно, он маленький.
